# Система бронирования столов в ресторане

## 1. Описание проекта

### Цель проекта

Разработать функциональность бронирования столов в ресторане через информационную систему.

Зарегистрированный пользователь должен иметь возможность выбрать ресторан, дату, время и количество гостей, после чего система проверяет наличие подходящего свободного стола и создаёт бронирование.

### Основной сценарий

Зарегистрированный пользователь → выбирает параметры бронирования → система проверяет доступность → создаёт бронирование → пользователь получает подтверждение.

## 2. Участники системы

| Участник | Роль |
|---|---|
| Зарегистрированный пользователь | Создаёт, просматривает и отменяет бронирования |
| Frontend | Предоставляет пользователю интерфейс |
| Backend | Обрабатывает запросы и реализует бизнес-логику |
| База данных | Хранит информацию о ресторанах, столах и бронированиях |

## 3. Границы проекта

### В проект входит

- просмотр ресторанов;
- выбор даты и времени;
- указание количества гостей;
- проверка доступности столов;
- создание бронирования;
- просмотр бронирования;
- отмена бронирования.

### В проект не входит

- регистрация и авторизация пользователя;
- оплата;
- доставка;
- отзывы;
- программа лояльности;
- управление персоналом ресторана;
- уведомления по SMS и электронной почте.

## 4. Уточнение требований

Перед разработкой необходимо уточнить:

1. Может ли один пользователь иметь несколько активных бронирований?
2. Можно ли изменить существующее бронирование?
3. Можно ли отменить бронирование?
4. За сколько времени до посещения можно отменить бронирование?
5. Как система определяет подходящий стол?
6. Можно ли объединять несколько столов?
7. Что происходит, если свободного стола нет?
8. Можно ли забронировать стол на текущую дату?
9. Как долго система должна хранить информацию о бронированиях?

### Зафиксированные решения

- пользователь уже зарегистрирован и авторизован в системе;
- регистрация и авторизация в рамках проекта не рассматриваются;
- один пользователь может иметь несколько бронирований;
- изменение бронирования не реализуется;
- пользователь может отменить бронирование;
- стол выбирается системой автоматически на основании количества гостей;
- объединение столов не поддерживается;
- если подходящего стола нет, система сообщает пользователю об отсутствии свободных столов.

## 5. User Stories

### US-01. Создание бронирования

Как зарегистрированный пользователь, я хочу забронировать стол на выбранную дату и время, чтобы посетить ресторан.

### US-02. Просмотр бронирования

Как зарегистрированный пользователь, я хочу просмотреть информацию о своём бронировании, чтобы знать дату, время и количество гостей.

### US-03. Отмена бронирования

Как зарегистрированный пользователь, я хочу отменить своё бронирование, чтобы освободить стол, если мои планы изменились.

## 6. Acceptance Criteria

### US-01 — создание бронирования

#### AC-01

Given: зарегистрированный пользователь указал ресторан, дату, время и количество гостей.

When: пользователь нажимает «Забронировать».

Then: система проверяет наличие подходящего свободного стола.

#### AC-02

Given: подходящий стол свободен.

When: пользователь создаёт бронирование.

Then: система создаёт бронирование со статусом «Подтверждено».

#### AC-03

Given: подходящих свободных столов нет.

When: пользователь пытается создать бронирование.

Then: система не создаёт бронирование и сообщает пользователю, что свободных столов нет.

## 7. Функциональные требования
| ID | Требование |
|---|---|
| FR-01 | Система должна позволять зарегистрированному пользователю выбрать ресторан |
| FR-02 | Система должна позволять выбрать дату бронирования |
| FR-03 | Система должна позволять выбрать время бронирования |
| FR-04 | Система должна позволять указать количество гостей |
| FR-05 | Система должна проверять наличие подходящего свободного стола |
| FR-06 | Система должна создавать бронирование при наличии свободного стола |
| FR-07 | Система должна присваивать созданному бронированию статус «Подтверждено» |
| FR-08 | Система не должна создавать бронирование при отсутствии свободного стола |
| FR-09 | Система должна позволять зарегистрированному пользователю просматривать своё бронирование |
| FR-10 | Система должна позволять зарегистрированному пользователю отменить бронирование |
| FR-11 | При отмене система должна изменять статус бронирования на «Отменено» |

## 8. Нефункциональные требования

| ID | Требование |
|---|---|
| NFR-01 | Система должна быть доступна пользователям круглосуточно |
| NFR-02 | Время ответа системы при проверке доступности стола не должно превышать 2 секунд при штатной нагрузке |
| NFR-03 | Система должна предотвращать создание двух активных бронирований одного стола на одну и ту же дату и время |
| NFR-04 | Данные бронирований должны храниться в базе данных |

## 9. Бизнес-правила

- BR-01. Бронирование может быть создано только при наличии подходящего свободного стола.
- BR-02. Стол не может одновременно иметь два активных бронирования на одну и ту же дату и время.
- BR-03. Отменённое бронирование не считается активным.
- BR-04. Количество гостей должно быть больше нуля.
- BR-05. Количество гостей не должно превышать вместимость стола, выбранного системой.

## 10. Use Case

### UC-01 «Забронировать стол»

Актор: зарегистрированный пользователь.

Предусловие: пользователь авторизован в системе.

### Основной сценарий

1. Зарегистрированный пользователь открывает форму бронирования.
2. Пользователь выбирает ресторан.
3. Пользователь выбирает дату.
4. Пользователь выбирает время.
5. Пользователь указывает количество гостей.
6. Система проверяет наличие подходящего стола.
7. Система находит свободный стол.
8. Система создаёт бронирование.
9. Система присваивает бронированию статус «Подтверждено».
10. Система отображает пользователю информацию о созданном бронировании.

### Альтернативный сценарий

На шаге 7 подходящий стол не найден:

1. Система не создаёт бронирование.
2. Система сообщает пользователю: «На выбранное время нет свободных столов».
3. Пользователь может изменить параметры бронирования.
